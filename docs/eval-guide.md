# Eval 设计指南

> 配套文档: [`PRD.md`](./PRD.md) §4.2 Eval Engine
>
> 本指南供两类读者: (1) 终端用户 — 在产品 UI 上写 Eval 时参考; (2) Worker / Eval Recommender 的 system prompt — 嵌入此文件保证 AI 推荐出的 Eval 符合规范。

## 1. 定义"什么是好"

第一个问题永远是: **你对一个"好结果"的定义是什么?**

比如一篇创作 skill 的"好":

- 全文是否控制在 1500 字以内?
- 开头 3 句有没有点清痛点?
- 标题有没有包含关键词?

把"好"拆成一组**是 / 否**的检查项, AI 才能稳定打分。

## 2. 黄金法则

> **每一个 Eval 都必须是一个 yes / no 问题。**
> 不是量表, 不是感觉判断, 必须是二元的。

**为什么?** 量表会叠加波动。如果你有 4 个 Eval 每个按 1–7 分评, 总分在不同运行间方差极大。
二元 Eval 才能给你**稳定、可靠、可复现**的信号。

辅助原则:

- **3–6 个 Eval** — 太多会被 Worker"钻空子", 太少信号不足
- **独立** — 两个 Eval 不能测同一维度, 否则重复计数
- **可观测** — 必须可被 LLM judge / regex / 长度 / 范围 / 代码运行**稳定回答**

## 3. 好 / 坏 Eval 对照

### 📝 文本 / 文案类

| ❌ 坏 Eval | 问题 | ✅ 好 Eval |
| --- | --- | --- |
| "这段文字写得好吗?" | 太模糊 | "是否完全没出现禁用词 [game-changer, here's the kicker, the best part]?" |
| "给它的吸引力打 1-10 分" | 量表 → 不可靠 | "开头第一句是否提到一个具体的时间、地点或感官细节?" |
| "它听起来像人写的吗?" | 主观, 评分不一致 | "输出是否在 150-400 字之间?" |

### 🎨 视觉 / 设计类

| ❌ 坏 Eval | 问题 | ✅ 好 Eval |
| --- | --- | --- |
| "看起来专业吗?" | 主观 | "图片中的所有文字是否都清晰可读, 没有截断或重叠?" |
| "给视觉质量打 1-5 分" | 量表 | "配色是否只使用柔和色调, 没有荧光色或高饱和颜色?" |

### 💻 代码 / 技术类

| ❌ 坏 Eval | 问题 | ✅ 好 Eval |
| --- | --- | --- |
| "代码干净吗?" | 主观 | "代码是否能在不报错的情况下运行?" |
| "它有遵循最佳实践吗?" | 模糊 | "输出中是否完全没有 TODO 或占位注释?" |
| | | "所有函数名是否都具有描述性?" |

## 4. 校验类型 (`check_kind`) 选型

| 类型 | 适合什么 | 典型 Eval |
| --- | --- | --- |
| `llm_judge` | 主观但二元的判断 | "开头是否含具体时间 / 地点?" |
| `regex` | 禁用词 / 必含关键词 | "是否完全不含 [禁用词列表]?" |
| `length` | 字数 / 行数范围 | "正文是否在 150-400 字?" |
| `range` | 连续指标包装为二元 | "ctr 是否 ≥ 0.6?" (用 metric `ctr` 比较) |
| `code` | 代码可运行 / 测试通过 | "pytest 是否全绿?" |
| `composed` | 多条件 AND / OR | "(含 CTA) ∧ (字数 ≤ 400)" |

**选型口诀**:

- 能 regex 就 regex (最稳定, 零 LLM 成本)
- 能 length / range 就别 llm_judge (省钱省时间)
- 主观判断才用 llm_judge, 且 prompt 要写得**只能回答 yes/no**

## 5. 常见错误

| 错误 | 问题 | 修正方法 |
| --- | --- | --- |
| Eval 太多 | 超过 6 个 → Worker 开始"钻空子" | 选出最重要的 3-6 个 |
| 过窄 / 过死 | 产出变得僵硬 (反复满足同一招式) | 检查真正关心的质量特征是否还在 |
| Eval 重叠 | 同一维度被重复计数 | 每个 Eval 测试**独立**维度 |
| Agent 无法稳定衡量 | 主观问题答案飘 | 翻译成**可观察信号** (具体词 / 长度 / 范围) |
| 写成量表 | "1-10 分有多吸引人" | 改成 "是否 ≥ X 标准?" 这种 yes/no |
| Prompt 太长 / 太抽象 | LLM judge 答案不稳定 | 单句、具体、举例 |

## 6. 建议工作流

1. 写下你对"好结果"的 5-10 条直觉描述
2. 把每条翻译成一个二元问题 (yes/no)
3. 删除重复的 / 主观无法稳定回答的, 留 **3-6 条**
4. 为每条选合适的 `check_kind` (能 regex 就 regex, 不行才 llm_judge)
5. 跑 5-10 个候选交付物, 看 Eval 分布是否合理 (不是全 yes 也不是全 no)
6. 如果发现 Worker"钻空子" (Eval 全过但交付物质量明显下降), 删一两条 Eval 或换成更难的检查

## 7. Worker prompt 中如何使用本指南

Eval Recommender / Worker 的 system prompt 应固定引用本指南:

```
你在为用户推荐 Eval 时, 必须遵守 docs/eval-guide.md 的黄金法则:
1) 每个 Eval 必须是 yes/no 二元问题
2) 推荐 3-6 个, 互相独立
3) 优先 regex / length / range, 主观判断才用 llm_judge
4) 拒绝量表式问题, 拒绝主观描述
输出 JSON: [{id, prompt, check_kind, config, weight}, ...]
```

这样 AI 推荐出的 Eval 默认就符合规范, 用户只需做微调。
